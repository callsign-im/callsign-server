# Callsign on a single EC2 host

Terraform for running `callsign-server` on one Graviton instance for about $20 a month. It fits a launch, a small team or a self-hosted install. When one machine is no longer enough, move to the managed, horizontally scalable stack in [`infra/aws-ecs`](../aws-ecs) (see [Moving to ECS](#moving-to-ecs)).

The dashboard (`app.callsign.im`) and the website (`callsign.im`) are deployed on Vercel and are not managed here. DNS stays at your provider: Terraform lists the records to add.

## Architecture

- **Host**: a `t4g.small` (2 vCPU, 2 GiB, arm64) running Ubuntu 24.04 with an Elastic IP. Docker Compose runs PostgreSQL 17, Valkey, the API, the worker and Caddy, which serves `api.callsign.im` with a Let's Encrypt certificate.
- **No SSH**: the security group only opens ports 80 and 443. Shell access and deploys go through AWS Systems Manager.
- **Data volume**: PostgreSQL and Caddy's certificates live on a separate encrypted gp3 volume, so the host can be rebuilt without losing data. Docker doesn't start until the volume is mounted.
- **Backups**: an hourly `pg_dump` to S3, kept for 30 days, and a daily snapshot of the data volume, kept for 7 days.
- **Application encryption**: a KMS key, `alias/callsign-<env>-data`, wraps the data keys that encrypt messages, ledger entries, contacts and rules before they are stored. Administrators can manage the key, but only the host's role can use it. See [docs/encryption.md](../../docs/encryption.md).
- **Images**: an ECR repository, `callsign-server`, with arm64 images tagged with the git SHA.
- **Email**: an SES domain identity with Easy DKIM plus SMTP credentials. You can use any other SMTP provider instead.
- **Cost alerts**: an AWS budget that emails you at 80% of actual and 100% of forecasted monthly spend, measured before credits.
- **CI/CD**: a GitHub Actions OIDC role that can push images, upload release files and run commands on this one host, and nothing else.

### Runtime configuration

Terraform keeps the containers' environment in a SecureString parameter, `/callsign-<env>/environment`, and every deploy writes it to `/opt/callsign/.env`:

| Variable | Value |
|---|---|
| `NODE_ENV`, `LOG_LEVEL`, `AWS_REGION` | `production`, `var.log_level`, `var.aws_region` |
| `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` | The local PostgreSQL container, with a password generated by Terraform |
| `REDIS_URL` | `redis://valkey:6379` |
| `PUBLIC_API_URL`, `APP_URL`, `SITE_URL`, `MAIL_FROM` | `https://api.<domain>`, `var.app_url`, `var.site_url`, `var.mail_from` |
| `SMTP_URL` | SES SMTP credentials, or `var.smtp_url` |
| `KMS_KEY_ID` | The data key's ARN |

The containers get AWS credentials from the instance role through IMDSv2, which is how the API reaches KMS.

## Prerequisites

- An AWS account, and credentials with administrator access for the first apply
- Terraform 1.10 or later, AWS CLI v2 with the [Session Manager plugin](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html), and `jq`
- GitHub CLI (`gh`), optional, for setting workflow variables
- Access to the DNS settings of your domain

## First-time setup

### 1. Create the state bucket

```sh
export AWS_REGION=us-east-1
BUCKET="callsign-terraform-state-$(aws sts get-caller-identity --query Account --output text)"

aws s3api create-bucket --bucket "$BUCKET" --region "$AWS_REGION"
# Outside us-east-1, also pass: --create-bucket-configuration LocationConstraint="$AWS_REGION"
aws s3api put-bucket-versioning --bucket "$BUCKET" --versioning-configuration Status=Enabled
```

The state holds the database password and SMTP credentials. New buckets block public access and encrypt objects by default, and state locking uses S3 native lock files.

### 2. Configure

```sh
cd infra/aws-ec2
cp backend.tf.example backend.tf              # set the bucket name
cp terraform.tfvars.example terraform.tfvars  # set github_repository and budget_alert_emails
terraform init
```

### 3. Apply

```sh
terraform apply
```

The host boots and installs Docker in a few minutes. Then pin its zone, so a later change in AWS's offerings never moves the data volume:

```sh
terraform output availability_zone  # copy into availability_zone in terraform.tfvars
```

### 4. Add the DNS records

Run `terraform output dns_records` and add each record at your DNS provider. At Namecheap, use **Advanced DNS** and put `host` in the Host field:

| Purpose | Type | Host | Value |
|---|---|---|---|
| API endpoint | A | `api` | the Elastic IP |
| SES DKIM (three records) | CNAME | `<token>._domainkey` | `<token>.dkim.amazonses.com` |
| DMARC policy | TXT | `_dmarc` | `v=DMARC1; p=none` |

Don't change the apex, `www` and `app` records that point at Vercel.

### 5. Configure GitHub

Create the `production` environment, copy the deploy settings into its variables and select this stack:

```sh
gh api -X PUT "repos/{owner}/{repo}/environments/production" > /dev/null

terraform output -json github_actions_variables \
  | jq -r 'to_entries[] | [.key, .value] | @tsv' \
  | while IFS=$'\t' read -r name value; do gh variable set "$name" --env production --body "$value"; done

gh variable set DEPLOY_TARGET --body ec2
```

If the environment restricts which branches and tags can deploy, allow `v*` tags.

### 6. Deploy

Run the **Deploy (EC2)** workflow from the Actions tab, or push a `v*` tag. Caddy requests the certificate as soon as the `api` record resolves to the host.

### 7. Leave the SES sandbox

New SES accounts can only send to verified addresses. Request production access in the SES console (Account dashboard, "Request production access") once the DKIM records verify.

## Deploys

`.github/workflows/deploy-ec2.yml` runs on `v*` tags and on manual dispatch when `DEPLOY_TARGET` is `ec2`. It assumes the deploy role through OIDC, then:

1. Builds the image on an arm64 runner and pushes it to ECR, tagged with the commit SHA. If the image already exists, it skips the build.
2. Uploads [`release/`](release) to the releases bucket under the same SHA.
3. Tells the host, through SSM, to download that release and run [`deploy.sh`](release/deploy.sh). The script writes `.env`, pulls the images, starts PostgreSQL and Valkey, runs the migrations, recreates the API, worker and Caddy, and waits until the API is healthy. Caddy holds requests for up to 30 seconds while the API restarts, so clients see a short pause instead of errors.
4. Checks `/healthz` over HTTPS.
5. Moves the `latest` tag to the deployed image.

To roll back, run the workflow on an earlier tag. The image already exists, so only the containers change. Migrations run on every deploy, so keep them backward compatible.

Changes Terraform makes to the environment parameter take effect on the next deploy.

## Operations

- **Shell access**: `eval "$(terraform output -raw shell_command)"`, then `cd /opt/callsign`. Commands there run as root with the host's role, which can decrypt stored data.
- **Status and logs**: `sudo docker compose ps` and `sudo docker compose logs --follow api worker`. Docker rotates the logs.
- **Backups**: `aws s3 ls "s3://$(terraform output -raw backup_bucket)/postgres/" --recursive | tail`. To restore a dump on the host:

  ```sh
  aws s3 cp s3://<bucket>/postgres/<path>.dump /var/tmp/restore.dump
  cd /opt/callsign
  sudo docker compose stop api worker
  sudo docker compose exec -T postgres sh -c 'pg_restore --clean --if-exists --username="$POSTGRES_USER" --dbname="$POSTGRES_DB"' < /var/tmp/restore.dump
  sudo docker compose start api worker
  ```

  Dumps and snapshots hold stored content encrypted, so they are only readable with this stack's KMS key.
- **Replacing the host**: `terraform apply -replace=aws_instance.host`, for example to adopt a newer Ubuntu image. The data volume and the Elastic IP move to the new host. A new host has no release, so run the deploy workflow afterwards.
- **Bigger host**: change `instance_type` (for example `t4g.medium`) and apply. AWS stops the instance, resizes it and starts it again, which takes a minute or two.
- **Teardown**: set `deletion_protection = false` and apply before you run `terraform destroy`. The data volume takes a final snapshot. The KMS key is deleted 30 days later, and encrypted content can't be read after that, so cancel the deletion if you plan to restore.

## Cost

Approximate us-east-1 on-demand prices with the default variables:

| Resource | Monthly |
|---|---|
| EC2 `t4g.small` | ~$12.30 |
| Public IPv4 address (Elastic IP) | ~$3.65 |
| EBS gp3, 20 GB root + 20 GB data | ~$3.20 |
| KMS key | $1 |
| Snapshots, S3 backups, ECR storage | under $1 at launch volumes |
| SES | $0.10 per 1,000 emails |

The baseline is roughly $20 per month before traffic. A `t4g.medium` adds about $12.

## Moving to ECS

Hand over the resources both stacks define instead of recreating them. Stored content can only be decrypted with the KMS key that wrapped it.

1. Remove the shared resources from this stack's state:

   ```sh
   terraform state rm aws_kms_key.data aws_kms_alias.data aws_ecr_repository.server aws_ecr_lifecycle_policy.server \
     'aws_sesv2_email_identity.main[0]' 'aws_iam_openid_connect_provider.github[0]'
   ```

2. In `infra/aws-ecs`, set `create_github_oidc_provider = false` and `terraform import` the KMS key, alias, ECR repository and SES identity before the first apply.
3. Apply the ECS stack and set `DEPLOY_TARGET` to `ecs`. Its IAM role and SMTP user have different names from this stack's, so both can run during the move.
4. Stop the API and worker here, copy the database into RDS with `pg_dump` and `pg_restore`, deploy, and point the `api` record at the load balancer.
5. Destroy this stack once the new one is serving traffic.
